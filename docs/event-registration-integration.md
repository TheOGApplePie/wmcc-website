# Event registration integration

The website calls `public_registration_open(event.id)` on the server. Migration 051 in the local dashboard makes this true only for a published event with a non-null form ID and an effectively open setting: no row defaults open, and a closed row with an elapsed `reopen_at` opens at read time. The function is security definer with an empty search path and grants anon/authenticated only execution of this boolean decision. It does not grant anon access to either registration table. The page additionally requires an upcoming session. An RPC failure hides both the link and embed, with only the event ID and error code logged. The event route is force-dynamic, uses the cookie-based server client, and the check endpoint returns `Cache-Control: no-store`; subsequent requests query again. Dashboard cache revalidation does not invalidate a separate website deployment.

The event-only form mounts through Cognito's per-form API. Its promise-returning `beforeSubmit` handler calls `GET /api/events/{database-id}/registration-availability` and blocks on a closed result, network error, invalid response or timeout. A message is announced via an alert. This is best-effort: direct Cognito links bypass it and a closure can race with submission. Test the actual embed and remount behavior with a safe form before release; Cognito documents registration but no handler removal method. Non-event embeds retain their prior behavior.

## Browser delivery

The event form's Cognito `afterSubmit` handler POSTs `{ formId, entry }` to the website's `POST /api/events/{eventId}/registrations`. The local dashboard migration 046 converts legacy JSON arrays into individual `event_registrations` rows and defines `append_browser_event_registration`, which inserts the entry object unchanged as a row. The RPC executes only as service role and checks the published event and currently configured form under a row lock. It deliberately does not recheck availability after Cognito has accepted an entry. Hosted migration state has not been verified.

The server validates the database ID, form association, JSON object and a 128 KiB body limit, requires same-origin JSON requests, and rate limits through Upstash. It uses `SUPABASE_SERVICE_ROLE_KEY` only on the server, along with the existing Supabase URL and Upstash environment variables. The route uses the first `x-forwarded-for` value or `x-real-ip`; the hosting provider and its proxy configuration cannot be verified from this repository. Before release, confirm that the proxy overwrites untrusted forwarded headers and supplies the actual client IP in the position used by the route. Otherwise the limiter may be bypassed or may group unrelated visitors. Origin and IP rate limits are abuse mitigations, not authentication. Missing configuration or rate-limit failures fail closed. Logs contain only event IDs and error codes, never entries. The browser reports a delivery failure and asks the visitor to contact WMCC without resubmitting; a timeout may occur after the database commit.

**These records are unverified browser input.** Anyone can call the public endpoint and fabricate data, even with the origin check and rate limit. The handler does not prove Cognito accepted an entry. It does not deliver if the browser closes or loses connectivity, and direct Cognito links bypass it. There is no verified provider ID or deduplication: repeated calls may append duplicates. A visitor may see Cognito's confirmation even when delivery fails, and an error message cannot be shown if the page closes. Staff must reconcile against Cognito before relying on completeness or authenticity. Do not use this browser path alongside a webhook without a verified shared identifier and deduplication.

Cognito documents JSON submit, update and delete webhook endpoints, with up to 15 retries over 72 hours for 4xx/5xx except 404, 410 and 413. Deleted entries omit entry and file links; file links expire quickly. Save & Resume does not trigger webhooks. Entry numbers are documented as stable and never reused, but their actual presence and form scope in both payloads must be confirmed with a safe test. Investigate ordering, duplicate updates/deletes, replay, recovery after exhausted retries, polling or manual reconciliation, and document retention semantics. Verify the account plan, actual configured form mapping, payloads, and supported authentication/signature mechanisms with Cognito; these are not available from this workspace. Do not assume a secret URL is a signed webhook or claim it is configured.

Sources: [Cognito client-side events](https://www.cognitoforms.com/support/62/data-integration/client-side-events), [webhooks](https://www.cognitoforms.com/support/66/data-integration/webhooks), [entry numbers](https://www.cognitoforms.com/support/81/entries/working-with-entries), [webhook plan information](https://www.cognitoforms.com/integrations/26/json-webhooks).

## Announcements and freshness

The homepage announcement query explicitly requires `review_state = 'approved'` even when a staff session permits broader database reads. It retains `publish_at IS NULL OR publish_at <= request time`, `expires_at > request time`, display order and pagination. A material edit that returns a record to draft removes it from later public requests until it is approved again, provided the date conditions are met. The homepage reads request headers and uses the cookie-based server client, so it is dynamically rendered; this query has no explicit persistent cache. A subsequent server request reads the current database state and evaluates the time again. An already open page, client-side navigation cache, intermediary cache or database replication delay can delay what a visitor sees; CMS revalidation cannot invalidate a separate deployment. The event detail page is likewise dynamic and its availability endpoint sends `no-store`; scheduled reopening is evaluated by the RPC on each check, not by a website cron.

Automated tests mock the database and Cognito client; they do not verify the dashboard's SQL rules, hosted grants, the hosting proxy, or a real Cognito embed. A safe-form browser test and full migration-chain verification remain release prerequisites.
